# ADR-0006：性能预算——只剩两条硬线，口径写死

- 状态：已接受（2026-09-11）
- 关联卡片：#14 性能三条复核

## 背景

原三条：单文件 ≤30MB（**用户取消**，2026-09-11）、空闲内存 ≤150MB、冷启动 ≤1s。选 Flutter 后内存构成变化，用户拍板口径为**最严的一种**。

## 决策

| 线 | 口径 | 依据 |
|---|---|---|
| 空闲内存 ≤150MB | **所有 lazydb 相关进程 RSS 总和**：Flutter 界面 + Go 后端 + 活动驱动代理 | 用户 2026-09-11 选定 |
| 冷启动 ≤1s | 双击图标到界面可交互（后端允许稍后就绪） | 保留原线 |

分项现状：Flutter 界面实测 63–100 MB（Reddit 63 MB 实测 + 社区口径 60–100+）；Go 后端 `推测:` 20–40 MB；驱动代理 ~4.3 MB/个（GoNavi 实测）。

**风险如实记录**：按上界推算总和可到 140+ MB，**贴线**。对策：

1. 空闲驱动代理一律不常驻（ADR-0002 生命周期），空闲时只有两个进程。
2. tracer bullet（MySQL 单链路）阶段即测三项真数，作为**验收门槛**而不是事后优化。
3. 界面侧克制用重库（动画、图表类包逐个审视）。
4. 超线且压不下来时回到 ADR-0001 的落选路径（换 Wails，界面进程 33.6 MB 实测）。

## 后果

- 无实测手段的阶段不拿这两条线当挡箭牌；有手段（tracer bullet 后）就是硬门槛。
- 体积无红线，但「能不引入的依赖不引入」写入设计原则。
